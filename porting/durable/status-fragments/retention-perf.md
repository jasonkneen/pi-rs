## Scheduler retention performance

The 20,000-deep retention case was latency-bound: ~20k serial JS<->native round trips plus one native commit per task, so wall time grew with machine load (base 23–104 s at equal load, 5/12 runs over 60 s). Native profiling found four quadratic costs in chain size: reconcile rebuilt overlay links for every finalized task; IndexSet/IndexMap shift_remove on `runnable`, `invocations` and `unloaded`; and a full `TaskTree::sizes()` per runtime commit. Native SQLite also made one worker-thread round trip per statement. Fixed in harness/ownership.rs (TaskTree::stage keeps cached links, has_drops), harness/scheduler.rs + harness/scheduler/ordered.rs (insertion-ordered indexes with O(log n) removal), and pi-chord sqlite/native.rs (in WAL/memory journal mode a transaction's statements and COMMIT run in place under the connection lock; uncontended BEGIN in place with busy_timeout 0; contended BEGIN and every rollback-journal connection stay on the worker, so a tokio worker blocks only for a statement's own CPU/IO, as node:sqlite blocks the JS thread upstream). Native 20k chain: MemoryStorage 8.8–15.4 s -> 2.1–2.8 s; SQLite 21.8–34.6 s -> 6.8–8.1 s. Stock 20k case: 13–45 s, 13/13 full-file passes at load 15–60 (base fails 5/12); bridge CPU 56 s -> 31 s. scheduler_fanout ms/call at 50…2000 calls: base 3.4/6.0/14.2/28.8/63.8/96.1 (quadratic) -> 0.38/0.34/0.30/0.28/0.28/0.32 (flat; the dominant fix is live::locate_slot in harness/tool/task.rs instead of re-encoding the live doc per nested call). Benchmarks: tests/scheduler_chain_retention.rs (opt-in chain and per-commit benches, contended-lock test). Remaining risk: ~5–6 serial bridge round trips per task, so above load ~150 the case can still pass 60 s.
